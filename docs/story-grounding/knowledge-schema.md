# Schema: `knowledge-continuity/1`

One JSON object per line in `corpus/knowledge_v1/{dev,heldout}.jsonl`, generated by
`corpus/knowledge_v1/build.py` (which checks the timeline, source order and every evidence id;
`--check` runs in CI). Versioning and the frozen held-out rule are as in
[schema.md](schema.md#versioning). Token-level annotation is the story-grounding corpus's job;
this one annotates knowledge.

## Record

| Field | Meaning |
|---|---|
| `schema_version`, `record_id`, `split`, `project_id`, `project_entities` | As in story-grounding |
| `timeline` | `[{id, label}]` in story order: `{"id": "chapter_02_scene_04", "label": "Chapter 2, Scene 4"}` |
| `sources` | `[{source_id, story_time_id, text}]`, in story order; `story_time_id` is on the timeline |
| `author_records` | `[{record_id, character_id, story_time_id, knowledge_state, text, note}]`: what the author says a character knows |
| `query` | `{kind, text, ...}`: below |
| `expected` | The correct answer: below |
| `gold_events` | `[{character_id, proposition, knowledge_state, acquisition_route, source_id}]` the events the passages should produce (optional) |

### Query kinds

| `kind` | Fields | Asks |
|---|---|---|
| `knows` | `character_id`, `proposition`, `story_time_id` | What the character knows about the proposition at that point (null = end of story) |
| `who_knows` | `proposition`, `story_time_id` | Who knows it at that point |
| `when_learned` | `character_id`, `proposition` | The story point of first learning |
| `leak_check` | none | Possible knowledge leaks in the whole draft |

`proposition`: `{subject, relation, object, location?, attribute?}`, entity ids and the **canonical**
verb (`hide`, not `conceal`; the first of its synonym group). `story_time_id` may name a group
(`chapter_02` is the end of its scenes).

### Expected

For `knows`: `knowledge_state` (or null), `status` (`STATED`, `UNKNOWN`, `CONFLICT`),
`acquisition_route` (or null), `evidence_ids` (source or author-record ids), `matches_canon`
(true / false / null), `note`. For `who_knows`: `who`, `status`, `evidence_ids`. For
`when_learned`: `story_time_id`, `status`, `evidence_ids`. For `leak_check`: `leaks`:
`[{character_id, action_source_id, proposition_source_id}]`.

`note` vocabulary: `no recorded acquisition found`, `first recorded acquisition is later`,
`possibility only`, `recorded as knowing earlier`, `story point not found`,
`question not understood`.

## The handover's knowledge record, as implemented

| Handover field | Here (`KnowledgeEvent.toJson`) |
|---|---|
| `character_id` | `character_id` (the host's character id) |
| `proposition_id` | `proposition`: `{subject, relation, object, location?, attribute?}`. The host's canonical record id replaces it where one exists |
| `knowledge_state` | `knowledge_state`: the handover's five plus `UNAWARE_IN_TEXT` (*added*) |
| `acquisition_route` | `acquisition_route`, or null when the text does not say |
| `story_time_id` | `story_time_id` |
| `evidence_refs` | `evidence_refs` (source ids); the answer carries `{source_id, start, end, quote, kind}`, `kind: author_record` for an author's entry |
| `status` | `STATED` on every event. DERIVED is not used: nothing here is inferred beyond what a sentence says |
| `valid_until` / `supersedes` | Both set when a later event for the same character, subject, verb and object has a different state or place |

`DERIVED` is unused on purpose: acquisition events come straight from a sentence, and the
persistence of knowledge after acquisition is part of how a query reads the timeline, not a
stored inference.
